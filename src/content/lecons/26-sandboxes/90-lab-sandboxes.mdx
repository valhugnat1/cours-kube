Sur ton PC, cluster kind `lab` de l'étape 0, avec Docker et un accès à Internet. Compte 45 minutes. Le nœud kind s'appelle `lab-control-plane` : c'est un conteneur Docker, dans lequel tu entres avec `docker exec` pour faire ce qu'un DaemonSet privilégié ferait chez un client. Kata n'est pas au programme : il demande KVM, rarement disponible dans un nœud kind.

## 1. Le noyau partagé

```bash
kubectl config current-context    # doit être kind-lab
kubectl create namespace lab26 && kubens lab26
kubectl run box --image=busybox:1.36 -- sleep 3600
kubectl wait --for=condition=Ready pod/box --timeout=60s
kubectl exec box -- uname -r
docker exec lab-control-plane uname -r
```

Les deux lignes affichent le **même noyau**. Le nœud kind est lui-même un conteneur : sous Linux, c'est le noyau de ton PC ; sous Docker Desktop, celui de sa VM. Un pod, un nœud, un noyau : la leçon 2 en une commande.

## 2. La chaîne, vue du nœud

```bash
kubectl get runtimeclass                                       # aucune
docker exec lab-control-plane crictl pods | head -5            # les pods, vus par containerd
docker exec lab-control-plane crictl info | grep -n runtimeType
docker exec lab-control-plane head -3 /etc/containerd/config.toml
```

`runtimeType` montre `io.containerd.runc.v2` : le seul vrai runtime du nœud est runc. Note la ligne `version = 2` ou `version = 3` du fichier de configuration : tu en auras besoin à l'étape 5.

## 3. Le privilégié, et le règlement qui le refuse

Écris `priv.yaml` :

```yaml
apiVersion: v1
kind: Pod
metadata: { name: priv }
spec:
  containers:
    - name: c
      image: busybox:1.36
      command: ["sleep", "3600"]
      securityContext: { privileged: true }
```

```bash
kubectl apply -f priv.yaml && kubectl wait --for=condition=Ready pod/priv --timeout=60s
kubectl exec box -- ls /dev | wc -l
kubectl exec priv -- ls /dev | wc -l
kubectl delete pod priv
kubectl create namespace lab26-strict
kubectl label namespace lab26-strict pod-security.kubernetes.io/enforce=restricted
kubectl -n lab26-strict apply -f priv.yaml
```

Le pod privilégié voit beaucoup plus de devices, ceux du nœud. Dans `lab26-strict`, l'API refuse le pod d'emblée : `violates PodSecurity "restricted:latest"`. C'est la leçon 3.

## 4. La RuntimeClass orpheline

Écris `sandbox.yaml` :

```yaml
apiVersion: node.k8s.io/v1
kind: RuntimeClass
metadata: { name: gvisor }
handler: runsc
---
apiVersion: v1
kind: Pod
metadata: { name: sandbox, namespace: lab26 }
spec:
  runtimeClassName: gvisor
  automountServiceAccountToken: false
  containers:
    - name: c
      image: busybox:1.36
      command: ["sleep", "3600"]
```

```bash
kubectl apply -f sandbox.yaml
kubectl get pod sandbox                     # ContainerCreating, et ça ne bouge pas
kubectl describe pod sandbox | tail -5
```

L'event `FailedCreatePodSandBox` dit `no runtime for "runsc" is configured`. Le YAML est valide, l'API l'a accepté, mais le nœud ne connaît pas ce runtime : c'est le piège des leçons 4 et 6. Laisse le pod en place.

## 5. Installer gVisor sur le nœud, comme un DaemonSet

Télécharge les deux binaires depuis les releases officielles de gVisor et copie-les dans le nœud :

```bash
ARCH=$(docker exec lab-control-plane uname -m)
URL=https://storage.googleapis.com/gvisor/releases/release/latest/${ARCH}
curl -fsSLO ${URL}/runsc && curl -fsSLO ${URL}/containerd-shim-runsc-v1
chmod +x runsc containerd-shim-runsc-v1
docker cp runsc lab-control-plane:/usr/local/bin/
docker cp containerd-shim-runsc-v1 lab-control-plane:/usr/local/bin/
```

Déclare le runtime dans containerd. Si l'étape 2 a montré `version = 2` :

```bash
docker exec lab-control-plane sh -c 'cat >> /etc/containerd/config.toml <<EOF
[plugins."io.containerd.grpc.v1.cri".containerd.runtimes.runsc]
  runtime_type = "io.containerd.runsc.v1"
EOF'
```

Avec `version = 3`, remplace `io.containerd.grpc.v1.cri` par `io.containerd.cri.v1.runtime`. Puis redémarre containerd et regarde le pod :

```bash
docker exec lab-control-plane systemctl restart containerd
docker exec lab-control-plane crictl info | grep -n runsc
kubectl get pod sandbox -w                  # le kubelet réessaie : Running après quelques secondes
kubectl exec sandbox -- uname -r            # 4.4.0 : la version que simule gVisor
kubectl exec sandbox -- dmesg               # les messages de démarrage du Sentry
kubectl exec box -- uname -r                # box, lui, voit toujours le vrai noyau
docker exec lab-control-plane ps aux | grep runsc
```

Deux pods sur le même nœud, deux noyaux différents vus de l'intérieur. La dernière commande montre le Sentry : un processus ordinaire du nœud, qui joue le rôle de noyau pour la sandbox. Si le pod passe en erreur au lieu de démarrer, c'est l'étage 3 du diagnostic de la leçon 10 : `docker exec lab-control-plane journalctl -u containerd --no-pager | tail -30`.

## 6. Les garde-fous d'un namespace de tenant

```bash
kubectl create namespace tenant-acme
kubectl label namespace tenant-acme pod-security.kubernetes.io/enforce=baseline
kubectl -n tenant-acme create quota sandboxes --hard=pods=2,limits.memory=512Mi
kubectl -n tenant-acme run s1 --image=busybox:1.36 -- sleep 3600
```

Refusé : `must specify limits.memory`. La quota exige des limites, et personne n'en a donné. Écris `limites.yaml` et applique-le :

```yaml
apiVersion: v1
kind: LimitRange
metadata: { name: defaut, namespace: tenant-acme }
spec:
  limits:
    - type: Container
      default: { memory: 128Mi, cpu: 500m }
      defaultRequest: { memory: 64Mi, cpu: 100m }
---
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata: { name: default-deny, namespace: tenant-acme }
spec:
  podSelector: {}
  policyTypes: [Ingress, Egress]
```

```bash
kubectl apply -f limites.yaml
for p in s1 s2 s3; do kubectl -n tenant-acme run $p --image=busybox:1.36 -- sleep 3600; done
kubectl -n tenant-acme get pods,resourcequota
kubectl -n tenant-acme exec s1 -- wget -qO- -T 3 http://example.com | head -3
kubectl -n tenant-acme create serviceaccount sandbox-ctl
kubectl -n tenant-acme create role creer-pods --verb=create,get,list,delete --resource=pods
kubectl -n tenant-acme create rolebinding sandbox-ctl --role=creer-pods --serviceaccount=tenant-acme:sandbox-ctl
kubectl auth can-i create pods -n tenant-acme --as=system:serviceaccount:tenant-acme:sandbox-ctl
kubectl auth can-i create pods -n lab26 --as=system:serviceaccount:tenant-acme:sandbox-ctl
```

À observer :

- `s1` et `s2` démarrent avec les limites par défaut, `s3` est refusé : `exceeded quota`. Un tenant ne remplit pas le cluster.
- Le `wget` échoue si ton CNI applique les NetworkPolicies. S'il passe, il ne les applique pas : c'est le constat de l'étape 4, à noter dans tes questions client.
- `auth can-i` répond `yes` dans `tenant-acme` et `no` dans `lab26` : le compte du contrôleur reste à son étage.

## 7. Où passe le temps au démarrage

```bash
kubectl -n lab26 run froid --image=python:3.12-slim -- sleep 3600
kubectl -n lab26 describe pod froid | grep -E "Pulling|Pulled|Started"
kubectl -n lab26 delete pod froid
kubectl -n lab26 run froid --image=python:3.12-slim -- sleep 3600
kubectl -n lab26 describe pod froid | grep -E "Pulling|Pulled|Started"
kubectl -n lab26 delete pod froid
kubectl -n lab26 run froid --image=python:3.12-slim --image-pull-policy=Always -- sleep 3600
kubectl -n lab26 describe pod froid | grep -E "Pulling|Pulled|Started"
```

Premier lancement : `Successfully pulled image … in` plusieurs secondes, l'essentiel du démarrage. Deuxième : `already present on machine`, le pull disparaît. Troisième, avec `Always` : le kubelet interroge à nouveau le registry, même si l'image est là. Multiplie par des milliers de sandboxes par jour : c'est la leçon 10, et le piège de la leçon 9.

## 8. Nettoyer

```bash
kubectl delete namespace lab26 lab26-strict tenant-acme
kubectl delete runtimeclass gvisor
rm runsc containerd-shim-runsc-v1 priv.yaml sandbox.yaml limites.yaml
```

gVisor reste installé dans le nœud kind jusqu'à `kind delete cluster --name lab` : c'est sans effet sur les autres labs, qui n'utilisent pas de RuntimeClass.
